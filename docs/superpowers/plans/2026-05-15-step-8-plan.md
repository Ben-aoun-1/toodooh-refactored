## Section 2 — Standing operating procedure (per-commit cadence)

### 2.1 Four-gate cadence (non-negotiable)

Between **every** commit:

```
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

All four must pass before the next commit fires. **Run in order.** typecheck catches
type errors; lint catches `no-console` / `no-explicit-any` etc; test catches behavioral
regressions; build catches Vite/Rollup dynamic-import path issues that the other three miss.

Drift tolerances:
- `pnpm typecheck`: must remain **58 errors** throughout. Any non-58 number is a regression.
- `pnpm lint`: must remain **370 problems (352 errors, 18 warnings)** throughout. Any drift
  is a regression.
- `pnpm test`: must remain **98 passing, 0 failing**. Any drift is a regression.
- `pnpm build`: gzip main bundle within **±0.5 kB of 131.42 kB**; NewCampaign chunk within
  ±0.5 kB of 25.77 kB. Hard halt at ±5 kB (Step-7 precedent).

If any drift appears, **hard halt** before committing — investigate, fix, re-run gates.
Do not commit a regressed gate.

**Lint-drift diagnostic shortcut:** if the lint count drifts and the new errors are
specifically `import/no-unresolved` (or its TypeScript-resolver equivalent), the
path-update sweep was incomplete — **fix the sweep**, don't tolerate the drift. This
is the most common failure mode for rename-heavy work and the cheapest to diagnose
(grep for the moved-file's old path; any survivors are missed updates).

### 2.2 `--no-verify` authorization

Authorized for the whole Step-8 commit chain per kickoff §3 (carried from Step 7). Workspace
`pnpm lint` total is the authoritative gate. lint-staged blocking on inherited per-file
errors is not.

**Authorization scope is bounded by the four-gate cadence above** — `--no-verify` bypasses
the pre-commit hook only; workspace lint still must pass per §2.1. If workspace lint fails,
do not `--no-verify` past it. The hook bypass exists to dodge pre-existing per-file lint
errors on moved files, not to hide regressions.

### 2.3 Eager-imports stability

`App.tsx`'s `React.lazy(() => import('./pages/Foo'))` boundaries do **not** change. Only the
**paths** update:

```diff
- const MyCampaigns = lazy(() => import('./pages/MyCampaigns'));
+ const MyCampaigns = lazy(() => import('./features/campaigns/pages/MyCampaigns'));
```

No new `lazy` boundaries, no removed `lazy` boundaries. Intra-feature internal imports stay
eager (per Step-7 precedent). Loading boundaries are out of scope for Step 8.

### 2.4 Line-count discipline (`wc -l` not eyeball)

Per Step-7 methodology learning #5 (Inventory & discovery discipline). Every commit summary
that cites a line count uses `wc -l` output, not eyeball estimates. Pre-extraction line
estimates drift 2–3× from actual.

### 2.5 Inventory-phase scope-expansion rule

Per Step-7 methodology learning #6. If a feature commit's inventory surfaces:
- a file the discovery doc didn't map (e.g., a file added since discovery),
- a file with zero imports (dead),
- a file touching follow-up issues #19 / #20 / #21,

**surface explicitly in the commit body** with three options for user response: accept, decline,
defer. Do not silently expand scope.

### 2.6 Pause-vs-diff verification

Per Step-7 methodology learning. The pause-after-commit summary describes intent; only the
diff confirms what landed. Every pause summary includes:

- The actual `git diff --stat` numbers (insertions, deletions, files changed).
- The exact gate numbers (typecheck count, lint count, test count, build size).
- Three randomly-sampled moved-file paths and a confirmation that `App.tsx` (or the consuming
  layout) resolves them at runtime — verified by `pnpm build` exit code 0.

If the pause summary numbers don't match the diff numbers, the writer described intent, not
the diff. Re-verify before the next commit.

### 2.7 Figma consultation rule

Per Step-7 methodology learning. Step 8 is rename-only — no UI/UX changes — so each
commit's inventory phase states: **"no UI/UX hesitancy in this commit; Figma check
skipped."** If a commit deviates from rename-only for any reason (e.g., needs to touch a
component's render to fix a relative-path issue), Figma is consulted per the standard rule.

### 2.8 Singular-vs-plural shadow grep

Per Step-7 methodology learning. Re-grep before each feature commit (cheap insurance) that
the move target's prospective new path doesn't collide with a hidden plural twin:

```
find features/<X>/ -name '*s.service.ts' -o -name '*.api.ts'
```

Discovery §4 confirmed 0 shadows; this is a paranoia check, not a real surface.

## Section 3 — Hard-halt criteria

Conditions that force a stop and ask the user before continuing:

1. **Any gate regresses** from the baseline numbers in §2.1 — typecheck > 58, lint > 370,
   test < 98 passing, or build outside ±5 kB on either main or NewCampaign chunk.
2. **A file with zero imports** is surfaced during inventory (potentially dead — Figma
   consultation needed before move).
3. **A file touches follow-up issues #19 / #20 / #21** beyond the placeholder home for #19
   (`AdvertiserPerformancePlaceholder.tsx` is the only authorized #19 file).
4. **A legacy shadow** surfaces (singular/plural twin, `.api.ts`, `.legacy.ts`).
5. **`App.tsx` lazy-import resolution fails at build** — Vite reports an unresolvable
   `import()` path.
6. **A move target collides** with an existing file in `features/`.
7. **A circular-import** edge appears in the build (Vite would warn) — usually a sign the
   feature boundary is wrong; halt and ask.
8. **A `--no-verify` commit fails** the workspace `pnpm lint` total (different from per-file
   blocking; this would be a real regression).
9. **The Node-20-not-in-PATH issue** re-surfaces during a commit and Husky fails — halt,
   re-export PATH, re-attempt; do not silently `--no-verify` past Husky engine errors.

## Section 4 — Pause-after-commit protocol

Every commit (Commits 1–9, plus the audit-refresh Commit 10) ends with a pause summary that
reports the following, in order:

### 4.1 Mandatory pause-summary contents

1. **Commit hash** + one-line subject.
2. **Files moved** (count) + **directories created** (count) + **directories emptied** (count).
3. **Gate numbers** (all four, from a fresh run, not assumed):
   - `pnpm typecheck`: exact error count
   - `pnpm lint`: exact problem count (errors / warnings)
   - `pnpm test`: suites / tests / failures
   - `pnpm build`: main chunk gzip, NewCampaign chunk gzip, delta from previous commit
4. **`git diff --stat`** summary: total insertions / deletions / files changed.
5. **Three spot-check moved files** with their new path + the consumer that imports them +
   confirmation that `pnpm build` resolved the import.
6. **Surprises** — anything outside expected inventory (zero-import files, scope expansions,
   shadow finds, gate drifts within tolerance). Empty list is fine; just say so.
7. **Next commit** — name + expected file count + expected gate-number deltas.

### 4.2 What I will NOT do in a pause summary

- Claim "all green" without citing the four numbers.
- Claim "no surprises" without listing them.
- Bundle the next commit's first action into the pause summary's tail (pause means stop).

### 4.3 Pause acceptance

User reads the pause summary, replies with "go" or feedback. No commit fires without explicit
go-ahead. Standing authorization in the kickoff covers `--no-verify`, not auto-advance
between commits.
