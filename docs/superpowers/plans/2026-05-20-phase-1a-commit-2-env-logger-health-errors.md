# Phase 1a Commit 2 — env validation + pino + /health + error handler

Second commit of the Phase-1 backend foundation. Commit 1 (`d723ae6`)
landed a minimal Fastify scaffold — no logger, no env validation, no
routes. Commit 2 makes the API usable as the foundation: env validated
at boot via zod, structured logs via pino (Fastify-native), `/health`
endpoint as proof-of-life, and a shaped JSON error handler that does
not leak 5xx detail in production.

The four pieces ship together because they reference each other: env
feeds `LOG_LEVEL` into the pino config; pino is the logger the error
handler calls; `/health` exercises the full boot chain (env → logger
→ Fastify ready). Splitting them creates intermediate states that
neither typecheck nor boot meaningfully.

This is a **rigid, mechanical** commit. No judgment calls expected
during execution — the file contents are fully specified in §11.

## §2 — Inventory phase

### §2.1 — Fastify v5 + pino integration

Fastify v5 ships pino as a built-in dependency and accepts a logger
config object via `Fastify({ logger: <opts | logger> })`. Passing a
**configuration object** (not a constructed logger) lets Fastify own
the lifecycle (request-scoped child loggers, serializers, redaction).
Plan-time confirmation:
- Fastify 5.8.5's `LoggerOptions` accepts `level`, `transport`,
  `serializers`, `redact`, `formatters`.
- Request scoping: `request.log.info(...)` produces child logs tagged
  with `reqId`; the auto-generated reqId can be replaced by setting
  `genReqId` and/or `requestIdHeader: 'x-request-id'`.

**Conclusion:** No `pino-http` plugin needed. Pass a pino config
object directly to `Fastify()`.

### §2.2 — Vitest 4 + tsx ESM resolution

apps/api is `type: module` (ESM). Vitest 4 defaults to native ESM
test execution and uses `tsx`-like loader (Vite's internal). It does
**not** depend on apps/api's `tsx` package — vitest brings its own
loader via Vite. The two coexist fine.

Test resolution path verified plan-time:
- vitest reads `vitest.config.ts` (auto-discovered alongside
  package.json).
- Default test glob `**/*.{test,spec}.{ts,tsx,js,jsx}` picks up
  `apps/api/tests/*.test.ts`.
- TS files run via vitest's loader; no separate `tsc` pass is needed at
  test runtime.

**Risk surface (low):** vitest 4's stricter ESM may reject default
imports from CJS-only packages. Our four runtime deps (fastify, zod,
pino, pino-pretty) all ship native ESM in their current majors. No
collision expected.

### §2.3 — `pino-pretty` placement: **runtime dep, not devDep**

`pino-pretty` is loaded at runtime via pino's `transport.target` string,
not via static import. If listed as a `devDependency`, production
builds shipped from `dist/` would crash on pino's transport thread
when dev/test config is accidentally used in production. But our env
schema gates `transport: { target: 'pino-pretty' }` behind
`NODE_ENV !== 'production'`, so production never references it.

Despite the gating: convention is to put `pino-pretty` in
`dependencies`, not `devDependencies`, because pino's transport thread
resolves it at runtime regardless of bundler graph. We follow the
convention. See pino-pretty's README ("Install: `npm install pino-pretty`,
not `--save-dev`").

### §2.4 — Zod 4 differences from zod 3 (for our shape only)

The env parser only uses these zod APIs:
- `z.object({...})` ✓ identical
- `z.enum(['a','b','c'])` ✓ identical
- `z.string()` ✓ identical
- `z.coerce.number()` ✓ identical (v4 keeps coerce semantics; "abc" still fails)
- `.default(value)` ✓ identical (v4 keeps the same defaulting semantics)
- `.parse(input)` throws `ZodError` ✓ identical
- `ZodError.issues` — **v3 had `.errors`; v4 deprecated `.errors` in favor of `.issues`**. Our error-formatter uses `.issues` (correct for v4).

**Conclusion:** Plan §11's env.ts is written against zod v4.4.3. No v3-only methods used.

### §2.5 — `tsconfig.json` and tests directory

Current `apps/api/tsconfig.json` has:
```json
"rootDir": "src",
"include": ["src/**/*.ts"]
```

Adding `tests/**/*.ts` to `include` while keeping `rootDir: "src"`
would cause `tsc` to error ("file is not under rootDir"). Three options
considered:

- **A.** Remove `rootDir`; include both. tsc emits `dist/src/...` +
  `dist/tests/...` flattened — breaks `main: "dist/server.js"`. **Rejected.**
- **B.** Single tsconfig with explicit `paths` carve-outs. Too clever.
  **Rejected.**
- **C.** Split into two configs (selected):
  - `tsconfig.json` — build config, `rootDir: "src"`, `include: ["src/**/*.ts"]`, `noEmit: false`. Used by `tsc` (build).
  - `tsconfig.test.json` — extends `./tsconfig.json`; overrides `noEmit: true`; `include: ["src/**/*.ts", "tests/**/*.ts"]`; drops `rootDir` (no emit, so no rootDir constraint). Used by `pnpm typecheck`.

  Precedent: apps/web uses TypeScript project references between
  tsconfig.app.json + tsconfig.node.json. Our split is the same shape,
  one layer simpler (no project-reference graph; the test config just
  extends the build config).

  Verified plan-time that ESLint reads files transparently without a
  specific tsconfig pointer (apps/api uses the default `import-x`
  resolver, not the TS-aware resolver scoped to apps/web).

## §6 — Hard-halt conditions

The executor halts and surfaces on any of:

1. **apps/api gate fails.** typecheck, lint, build, or fewer than 3 tests pass.
2. **Any root gate regresses.** Root typecheck > 51, lint > 1, test < 163, build > ±0.5 kB.
3. **Vitest + tsx ESM resolution fails** in a way §2.2 didn't anticipate (e.g., a `Cannot use import statement outside a module` from one of our packages).
4. **`pino-pretty` loaded in production NODE_ENV.** A boot with `NODE_ENV=production` must not include `pino-pretty` in pino's transport target.
5. **`/health` response shape mismatch** vs §11 schema.
6. **Error-handler leaks 5xx detail in prod.** The body for a 5xx in `NODE_ENV=production` must contain only the generic message + statusCode + requestId; no stack trace, no internal message.
7. **Malformed env passes validation.** `PORT='abc'` must reject at boot; if Fastify boots, the validation was bypassed.
8. **Husky/lint-staged hook errors** on the new files. Investigate root cause (Node version, lint rule); do not bypass with `--no-verify`.
9. **Inventory finding during execution** that §2 did not surface (e.g., a vitest ESM edge case, a zod v4 method that does not exist). Halt → CF-9 → architect decides.

```ts
const EnvSchema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  PORT: z.coerce.number().int().positive().default(4000),
  HOST: z.string().default('0.0.0.0'),
  LOG_LEVEL: z.enum(['trace', 'debug', 'info', 'warn', 'error', 'fatal']).optional(),
});

export type Env = z.infer<typeof EnvSchema> & { LOG_LEVEL: NonNullable<z.infer<typeof EnvSchema>['LOG_LEVEL']> };

export const parseEnv = (raw: NodeJS.ProcessEnv): Env => {
  const result = EnvSchema.safeParse(raw);
  if (!result.success) {
    const issues = result.error.issues
      .map((issue) => `  - ${issue.path.join('.')}: ${issue.message}`)
      .join('\n');
    throw new Error(`Invalid environment configuration:\n${issues}`);
  }
  const parsed = result.data;
  const logLevel: Env['LOG_LEVEL'] =
    parsed.LOG_LEVEL ?? (parsed.NODE_ENV === 'production' ? 'info' : 'debug');
  return { ...parsed, LOG_LEVEL: logLevel };
};

export const env: Env = parseEnv(process.env);
```

```ts
import type { FastifyError, FastifyReply, FastifyRequest } from 'fastify';

import type { Env } from './env.js';

interface ErrorResponseBody {
  error: string;
  message: string;
  statusCode: number;
  requestId: string;
}

export const buildErrorHandler = (env: Env) => {
  return (err: FastifyError, request: FastifyRequest, reply: FastifyReply): void => {
    const statusCode = err.statusCode ?? 500;
    const requestId = request.id;

    request.log.error(
      { err, method: request.method, url: request.url, requestId },
      'request failed',
    );

    void reply.header('x-request-id', requestId);

    const isServerError = statusCode >= 500;
    const isProduction = env.NODE_ENV === 'production';

    const body: ErrorResponseBody = {
      error: err.name || (isServerError ? 'Internal Server Error' : 'Bad Request'),
      message: isServerError && isProduction ? 'Internal Server Error' : err.message,
      statusCode,
      requestId,
    };

    void reply.status(statusCode).send(body);
  };
};
```
