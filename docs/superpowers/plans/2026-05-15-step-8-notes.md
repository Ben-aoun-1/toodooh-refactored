## CF-1 amendment — anchored consumer grep (added at Commit 5)

When grepping for service consumers (CF-8 verification), anchor the pattern with
closing-quote-and-escaped-dot (e.g. `'screens\.service'`, `'auth\.service'`) to
avoid substring-matching sibling services. Commit 5 over-counted `screens.service`
consumers by 2 (12 reported, 10 actual) because the unanchored substring matched
`admin-screens.service`.

Apply going forward for all service-consumer greps, **especially where prefixed
siblings exist** (admin-X, campaign-X, owner-X variants).

Example before/after:
```bash
# Wrong — substring matches admin-screens.service
grep -rln "services/screens\.service\|screensService"

# Right — anchored
grep -rln "from '.*services/screens\.service'\|\\bscreensService\\b"
```

## CF-1 — Sed-pattern coverage checklist (Adjustment A)

Before running sed for any feature commit, enumerate which **three import-path
shapes** are in play for the files being moved:

1. **External imports** from outside the moving directory: `'../X'`, `'../../X'`,
   `'../../../X'`, etc. The exhaustive external-directory list is:
   - `lib/`, `assets/`, `services/`, `stores/`, `types/`, `pages/`
   - `components/`, `hooks/`, `contexts/`
   - **`constants/`** (added after Commit 1 caught it missed)
   - `utils/`, `data/`
   - `features/` (for cross-feature imports after auth lands)

2. **Self-sibling imports** inside the moving directory: `'./X'` patterns.
   These are subtle and easy to miss because sed default patterns look for `..`.
   Commit 1 missed `./admin.store` in `stores/auth.store.ts` — when
   `stores/auth.store.ts` moved out of `stores/`, its `'./admin.store'` sibling
   reference broke (now needs `'../../../stores/admin.store'`).

   **AMENDED at Commit 7 — covers BOTH static and dynamic import forms:**
   - static: `from './X'`
   - dynamic: `import('./X')` (e.g., `const { x } = await import('./X')`)
   Commit 7's `admin-video.service.ts` had `await import('./campaign.service')`
   and `await import('./balance.service')` — the static-only grep missed both;
   typecheck regression was the catch. **Per-commit check covers both:**
   `grep -nE "from '\./|import\('\./" <file>` — any hit needs rewriting.

   **Also AMENDED at Commit 7 — generic vs prefixed service patterns.**
   sed rewrite rules for `'../../services/X'` must include a generic catch-all
   for services that stay at root (`global-configuration.service`,
   `balance.service`), not only the specific prefixed names being moved. Commit 7
   missed the generic `'../../services/global-configuration.service'` bump
   because the sed only listed admin-prefixed service names.

3. **Intra-feature siblings post-move** become `'./X'` again automatically when
   the relative depth lines up (e.g., `features/auth/components/LoginForm.tsx`
   importing `'../stores/auth.store'`). Trust git rename detection here; no
   sed needed.

4. **Depth-classification-by-inspection** (added at Commit 6). When sed groups
   files by directory pattern, the assumed depth must match the actual path
   depth of each file in the group. Never assume "this file looks like it's at
   the same depth as its directory peers" — verify by exact path inspection
   before sed.

   Worked example: Commit 6 `components/AdvertiserNotificationsBell.tsx` was
   depth 1 (direct child of `components/`), while `components/layout/*.tsx`
   files were depth 2 (one subdir deeper). Initial Group B sed applied +1
   depth bump uniformly; AdvertiserNotificationsBell needed +2 because it was
   already one level shallower than assumed. Caught by exhaustive grep before
   gates ran. Without pre-classification, the typecheck regression would have
   been the catch-mechanism — works but more expensive than upfront
   inspection.

   **Apply going forward:** for each commit's sed plan, list every moving file
   with its source path and computed target path explicitly. Verify depth
   bumps per-file, not per-group.

**Surface in pause summary:** under spot-check or surprises, state which shapes
were in play and whether all three were handled.

## CF-2 — Standard four-gate cadence with sed-aware autofix (Adjustment B)

The four-gate cadence in practice for Step 8 is:

```
typecheck → sed → (eslint --fix scoped to touched files) → lint → test → build
```

**Why the autofix step is routine, not regression-tolerance:**
sed-injected `features/*` paths land at the original line positions. Alphabetical
sort then requires reordering on every consumer of every moved file. This appears
as a temporary `import-x/order` lint spike on every Step-8 commit.

**Procedure:**
1. After sed, run `pnpm exec eslint --fix $TOUCHED_FILES`.
2. Then measure the lint gate against post-autofix state.
3. Lint must return to baseline 370.

**Halt-condition refinement:**
- Order-only spike → routine, fix with autofix, proceed.
- **Spike survives autofix** (some non-order rule regressed) → halt and
  investigate. THAT is the real regression signal.
- Per Commit 1: `import-x/order` was the entire +35; autofix returned lint to 370
  cleanly. No other rules regressed. Expected pattern.

**Autofix blind spot (added at Commit 7).** `eslint --fix` cannot reorder
imports across a CSS / side-effect import (`import 'x/y.css'`). When a
path-rewritten file has a side-effect import interleaved between parent
imports, autofix leaves an `import-x/order` error it cannot resolve. Commit 7's
`GeographicZonesManagement.tsx` had `import 'leaflet/dist/leaflet.css'` between
`'../../screens/...'` and `'../../../lib/...'`; the order error needed a manual
reorder. **Check after autofix:** if `import-x/order` count is non-zero, grep
the remaining errors — any in a file with a side-effect import needs manual
fix.

## CF-3 — Chunk-hash signal (Adjustment C, REVISED at Commit 2)

**REVISION at Commit 2:** the original "hashes byte-identical" framing was too
strict. Source-string changes (e.g., a lazy-import path updated, a `from '../X'`
rewritten) propagate to chunk hashes because the source becomes part of the
chunk's content-hashed output.

**Soft signal, not a gate:**
- Hash *identity* is a happy outcome — happens when Vite's module graph collapses
  to the same final bundles (Commit 1's case: many path rewrites but same modules
  resolved).
- Hash *change* is normal when source content changes — every Step-8 commit will
  show some chunk-hash changes for the chunks whose source touched.

**What still triggers halt:**
- A chunk hash changes AND the diff doesn't explain it (no source change in any
  file that lands in that chunk).
- A chunk's **gzip size** drifts past ±0.5 kB without obvious reason.
- A NEW chunk appears unexpectedly (Vite split something it didn't before).
- A chunk DISAPPEARS unexpectedly (Vite collapsed something).

Use the chunk hash list below as a **reference**, not a gate; cross-check against
the diff when a hash changes.

**Stronger than gzip-size match — preserved for posterity:** chunk hashes
byte-identical to baseline are still the strongest possible proof of pure-rename
when they happen, but they are not the expected outcome.

## CF-4 refinement — AST sweeps exceed grep predictions at scale (added at TBD-C)

At sweep scale (500+ imports), AST-based codemods systematically find more imports
than grep-based discovery predicts. Discovery's grep pattern-matches on **syntax**
(e.g. `'../'`); AST resolution follows **path semantics**. The mismatch surfaces
especially with `./`-prefixed cross-directory imports (e.g. `App.tsx` →
`./features/...`, which a `'../'` grep misses entirely).

Worked example: TBD-C discovery predicted ~463 imports; the AST codemod counted 517
(+11.7%). Pattern: future sweeps of this scale should expect the AST count to exceed
the grep count by 5–15%. Discovery counts are lower bounds, not estimates.

## CF-12 — measure gates in the committed end-state (added at TBD-C)

Gate numbers in a pause summary must be measured in the **committed end-state**,
after any setup/teardown operations have completed. If a commit involves
install/uninstall dances or other transient state, run gates after all transient
state has resolved.

Worked example: TBD-C Commit 2's lint number (357) was measured while `ts-morph`

measure the *committed* state and explain transients honestly — pause-summary
readers reason about what landed, not the working-tree state at gate-run time.

## TBD-C — path-alias rule (added at TBD-C)

The `@/*` alias (→ `./src/*`) was added in TBD-C. The rule for which imports get
aliased, **refined during TBD-C discovery**, replaces the naive "`./` vs `../`"
heuristic:

- **ALIAS** — any import whose **resolved target is in a different directory** from
  the importing file. The written form (`./` vs `../`) is irrelevant; what matters
  is the resolved target directory.
- **RELATIVE** — any import whose resolved target is in the **same directory** as
  the importing file (a true intra-directory sibling). Left as `./X`.
- **SKIP** — external package imports (do not start with `.`).

Worked example: `App.tsx` is at `src/App.tsx`. Its `import('./features/auth/pages/Login')`
resolves to `src/features/auth/pages/Login` — a *different* directory from `App.tsx` —
so it aliases to `@/features/auth/pages/Login`. By contrast `Step6` → `./Step5` (both
in `src/features/campaigns/pages/new-campaign/`) is a same-directory sibling, stays
relative. The naive heuristic would have left App.tsx's 46 cross-directory imports
un-aliased purely because they start with `./` — the resolved-directory rule fixes that.

The sweep was AST-driven (ts-morph), covering static `import`/`export … from` and
dynamic `import('…')` including the `React.lazy(() => import('…'))` nesting. Codemod
recorded at `apps/web/scripts/codemod-add-path-aliases.ts`.

## CF-7 — Two-tier push policy (added at Commit 3)

Standing instruction from the user. Effective for the rest of Step 8.

**Doc commits** (plan, discovery, notes, audit refresh):
- commit → **push immediately** → pause summary (include GitHub URL)
- Reasoning: docs are reviewed against the rendered version on origin.

**Code commits** (the 9 feature moves: Commits 1–9):
- commit → four gates → pause summary (local hash only) → user "go" → **then push**
- Reasoning: local-only until approved means a bad commit can be amended or
  reverted without polluting origin/main with a public revert.

**Notes file edits** mid-Step-8 (like the CF-3 softening at Commit 2):
- Land as own micro-commit; push immediately.
- Do NOT bundle into feature commits going forward. Commit 2's bundling was a
  one-time `git add -A` accident.

**Pause-summary content**:
- Doc commits: include the GitHub URL of the pushed commit.
- Code commits: include the local hash only; URL appears after "go" + push.
- "Next commit" line stays as-is in both cases.

**Amendment (Step 11 · Commit 6).** The two-tier split is relaxed: ordinary
code commits now **push in the same flow as the gate sweep** — commit → four
gates → push → pause summary (with URL) — with no separate hold-local-then-go
round-trip. Doc commits are unchanged (push immediately, CF-6). The hold-local
discipline is **retained, at the executor's discretion, for high-risk commits**
— codemod runs, large-diff refactors, anything where a public revert would be
costly — which still get commit → gates → local-hash pause → "go" → push. The
Step-11 chain showed why: every commit ended green and was approved verbatim;
the round-trip added latency without catching anything. The escape hatch stays
for the genuinely risky case.

# Step 10 carry-forwards — formalized at the Commit 9 audit refresh

Step 10 (React Query migration, roadmap #6) generated four numbered
carry-forwards beyond the Step-8 set. They were used as "candidates"
through the migration and are promoted here to formal rules.

## CF-13 — per-feature query-key factory

Each feature folder owns one `hooks/queryKeys.ts` exporting a named
`<feature>Keys` factory: hierarchical readonly tuples
`['<feature>', '<view>', ...args]`; `<feature>Keys.all` is the
feature-wide invalidation prefix (React Query matches keys by prefix).
A single global `queryKeys` object was rejected — it would make every
feature commit edit one shared file and contradicts per-feature-folder
ownership (D6).

**First amendment — bundle `useMutation`s by mutationFn identity, not
handler identity.** N handlers calling the same service method (or the
same `supabase.from(...).update(...)` shape) with different args = ONE
`useMutation` whose argument is the patch. Worked examples: Step 2b's
admin-side writes collapsed 8 handlers → 3 mutations; Commit 7a's three
`campaigns.update` call sites (existing-draft save, insufficient-balance
revert, cart-add finalize) collapsed to one `updateCampaign`; Commit 8's
`markRead` + `markAllRead` collapsed to one mutationFn taking `string[]`.

**Second amendment — feature hooks AND the `queryKeys` factory are
created by the commit that migrates the first consumer**, under the
feature that owns the service (D6) regardless of which feature contains
the consumer. Worked examples: Commit 5 was skipped because its would-be
consumers had no first consumer yet; 6c defined `screensKeys.predefinedZones()`
which 7a (a different commit, a different feature's page) was the first
to consume — the first cross-commit factory→consumer handoff; 7a's
`useVideoUploadMutations.createVideoEntry` documented "(a) reader absent",
and 7b retroactively wired `campaignsKeys.myApprovedVideos` into its
invalidation graph once `useMyApprovedVideos` (the reader) landed — the
second such handoff, closed.

## CF-14 — cross-feature invalidation graph with (a)/(b) classification

Every `useMutation` enumerates, in a comment above its `onSuccess` /
`onSettled`, every query key whose **user-visible displayed data
changes** — not every key that *could* be stale. Each key is classified:

- **(a) within-session** — the mutating session and the consumer share
  one `QueryClient`; `invalidateQueries` delivers a real refetch.
- **(b) cross-session cross-role** — consumer is a different user /
  role / browser session. The mutating session's `invalidateQueries`
  is a **no-op against keys it never cached**; it is kept for intent +
  hybrid-session defence, and actual freshness rides the consumer's
  `staleTime`.

**Sub-clarification — over-invalidation is acceptable, under-invalidation
is not.** Invalidating a `.all` prefix (or a key no consumer reads yet)
is harmless — a redundant refetch or a no-op. *Missing* a key whose
displayed data changed is the exact bug class Step 10 exists to kill
(hard-halt #7). When in doubt, invalidate wider.

Worked examples: Commit 6a `approveRecharge` (1×(a) the admin recharge
list, 2×(b) the advertiser's balance + dashboard); 6c's catalog/zone
mutations reach `OwnerPerformance` / `EventManagement` as (b)-class
cross-session; 7a `useConfirmCartLaunch` reaches admin monitoring +
owner approvals as (b); 8's mark-read is the clean opposite — purely
(a), single-session, zero (b) reach.

**D1 cross-session firewall (incidental positive).** D1's keep-auth-in-
Zustand rule incidentally removes a class of (b)-class invalidations
from Step 10's scope: user-visible auth/session state propagates through
the auth store's own mechanisms (the Supabase auth listener), not query
invalidation. Phase 1's realtime layer must therefore consider two
channels — React Query refetch for query-cache data, auth-store
mechanisms for identity/session data.

## CF-16 — consumer-side reference-identity discipline

Hook returns that consumers depend on for reference stability must not
be wrapped in always-fresh default expressions. Three sub-rules:

1. Hooks return raw query data when consumers key memos/effects off it;
   a `data ?? []` at the *call site* churns every dependent hook.
2. User-driven resets call the seeder directly with cached data, not
   `invalidate` (structural sharing may hand back the same reference).
3. Mirror / derive effects guard `if (data)` before seeding.

Worked examples: 5a `OwnerScreens` returns raw query data; 5c1's
"Annuler" buttons re-seed from cache rather than invalidating; 5c2
`useOwnerCampaignsOverview` returns raw data; 7b `OwnerCampaigns`'
`const campaigns = overviewCampaigns ?? []` churned three dependent
hooks (caught at gate-run time as three new `exhaustive-deps`
warnings) and was wrapped in `useMemo` — the discipline applies to
`?? []`-default churn, not only to derive-from-query effects.

## CF-5-extended — typecheck-drift discipline on touched files

Self-introduced transients (an orphaned import after an effect is
removed; an unused `const` after its sole consumer moves to a hook)
are fix-inline-no-protocol. Genuine incidental drift from real work
requires: surface it, justify it, and **stash-diff verify** the count
is honest (`git stash` → typecheck → compare per-file) — removed-error
masking via a widened type is a regression even when the total looks
flat. A migration commit does **not** fix unrelated pre-existing
issues it merely passes near (e.g. a dead type carrying a Cat-A error,
a discarded `Promise.all` result) — those are surfaced as TBDs, not
silently cleaned.

## CF-17 — couple the conversion strategy to the available verification capability (added at Step 11 Commit 4)

When a refactor's correctness can only be confirmed by a capability the
executor does not have — rendered-pixel comparison, a running dev server, a
manual click-through — do not pick the "best" strategy and hope; pick the
strategy whose correctness is verifiable with what _is_ available.

Step 11 Commit 4 (jsx-a11y interaction rules) had to keyboard-enable 24
click-only elements. The ideal fix varies per element (native `<button>` here,
`role` there), but "ideal" would have needed pixel verification to prove no
visual regression — unavailable to the agent. The chosen strategy instead made
the available verification _sufficient_: 100 % keyboard-fallback
(`role="button"` + `tabIndex={0}` + `onKeyDown`, **no tag or structure
change**) produces zero visual change _by construction_, so a plain `git diff`
review is a complete proof. Strategy was bent to fit the verification, not the
other way round.

Generalises to: codemod design (prefer transforms whose output is diff-
verifiable), type-narrowing (prefer narrowings the typechecker confirms over
ones needing runtime proof), and any "we can't test this directly" situation.
State the verification capability you have _before_ choosing the approach.

**Companion gate (from the Commit 5b codemod regression).** A codemod's
verification gate must assert **"no _unrelated_ rule/metric moved"**, not just
"the target metric improved". Commit 5b's first run drove `no-useless-catch`
to 0 while silently raising `no-explicit-any` by 13 (dropped `eslint-disable`
trivia — see the Step 11 plan doc closeout, item 9). Total-count parity hid it:
the target rule hitting zero masked the sibling rule rising. Always diff the
_per-rule_ breakdown across a codemod run, never just the total.

## CF-18 — token-tokenization inventory: three axes, two phases (added at Step 12)

When migrating a hardcoded value onto a design token, the canonical value is the
**seed of the inventory, not the complete set**. A production codebase couples
the canonical value to companions, encodes it in multiple forms, and — if a
prior migration was left unfinished — already holds it under both the old and
the new value. The inventory (and the fix tooling) must walk **three axes**:

- **Axis 1 — Neighbourhood.** Perceptually-near or structurally-related values
  doing hover/gradient/disabled/focus/variant work. A brand colour travels with
  a shade family. Grep the hex _neighbourhood_ (`#00xxxx`, `#76xxxx`), not just
  the canonical value.
- **Axis 2 — Representation.** The same value in alternate encodings — hex,
  `rgb()`, HSL, integer tuples (`[0,179,166]` for jsPDF/canvas), named colours,
  CSS custom properties. A grep for the hex spelling misses every library that
  encodes the colour differently.
- **Axis 3 — Source/Target.** During a migration, **both** the value migrated
  _from_ and the value migrated _to_. A partial/in-progress migration leaves the
  codebase in a mixed state; grepping only the from-value silently misses every
  site already converted to the target.

…across **two phases**:

- **Inventory phase** — grep all three axes; classify each finding by role;
  forecast the token tally _including_ opacity-modifier-variant conversions
  (`bg-X/90` etc. create new token references — Step 12 predicted 602, actual
  633, the 31-delta was unforecasted Commit-3b `/90` conversions).
- **Fix phase** — the migration tooling must reach all three axes too. A
  className-gated regex is structurally blind to inline-`style` and
  library-runtime (jsPDF/canvas/SVG) colour usage; those are a separate
  Pattern-B fix scope.

**Worked examples (Step 12):**
1. Commit 2 — transitive `@apply` (CSS coupling): the dead `leviosa-*` removal
   was a 7-class atomic unit because `@apply` is transitive; a split commit
   broke the PostCSS build.
2. Inventory §2 → Commit 3b — **Axis 1**: a 5-shade teal hover/gradient family
   (45 occ) the canonical `#00B3A6` grep missed.
3. Inventory §2 → Commit 4 — **Axis 2**: jsPDF `[0,179,166]` RGB tuples (3 of 4
   sites missed; the 4th caught only via a stray `// #00B3A6` comment).
4. Commit 3c → Commit 4c — **Axis 2 at the fix phase**: the className-gated
   contrast regex could not reach inline-`style` or jsPDF; 16 contrast fixes
   landed in a separate Pattern-B pass.
5. Inventory §2 → Commit 4b — **Axis 3**: 115 occurrences already on the target
   `#76E6AB` (a previous developer's incomplete rebrand) + an 86-occurrence
   6-shade mint family — fully invisible to the from-value grep.

**Sub-notes.**
- _Partial-migration mid-state._ The inherited codebase reflects migrations the
  previous developer started and left unfinished. Do not assume "migrating X→Y"
  implies a uniform-X starting state. Phase-1 inventory phases should assume
  mixed state until proven otherwise.
- _Sibling-attribute pairing._ When a fix pairs two attributes (a `text-*` with
  a `bg`/`style`), verify the pairing per-site — don't blind-swap on a
  proximity window. Step 12 Commit 4c: `MyRecharges:160` was a false positive
  (its own text colour was inline `color:'#1A3C34'`; a ±6-line scan caught a
  neighbour's `text-white`). Same shape as Commit 3b's gradient-pairing check.
- _Transient environment faults._ Segfaults / spurious parser errors on
  untouched lines are infrastructure, not code. Recovery is
  retry-after-verification: confirm `tsc` parses clean (rules out a real syntax
  error), stash-test the pre-commit baseline builds (rules out a regression),
  then retry. Document the retry in the pause summary.

CF-18 generalises beyond colour — Phase 1 will tokenize fonts, spacing, shadows;
each sweep needs the three-axis discipline (e.g. typography: every weight/style
of the canonical family, not just the family name).

## CI gating discipline (added at Step 13 — not a numbered CF)

Three CI-methodology notes from Step 13 (get-CI-green). Kept as one standalone
section rather than grafted onto CF-18 — CI bash output-parsing and colour-token
inventory are different domains; bundling dilutes both.

**Baseline-as-ceiling gating.** When a cleanup phase hands off to CI before all
debt is cleared, CI verifies **"no regression past the committed baseline"**,
not "exit 0". The baseline is a committed constant (Step 13: `TYPECHECK_BASELINE=51`,
`LINT_BASELINE=1`, inline in `ci.yml`, each commented with the issue that owns
the debt — #15). The gate **fails on `count > baseline`** and emits a non-failing
`::notice::` on `count < baseline` (prompting a manual ratchet-down). CI never
self-commits the baseline. When the owning issue lands, the baseline ratchets to
0 and the gate becomes a strict `== 0`.

**Output-parse fragility.** A baseline gate parses tool output with `grep`
(`grep -c 'error TS'` for `tsc`; `grep -oE '[0-9]+ error'` for ESLint). That
parse is coupled to the tool's output format — **re-verify it after any version
bump** of the underlying tool. And when applying a wrapper pattern to multiple
workflow steps, **verify each step's diff individually** shows the wrapper — not
just that "the pattern was applied somewhere".

**CI-diagnosis discipline — verify `headSha` before reading a run's log.** CI
runs are tied to specific commits; different commits produce different CI states
from their tree-state at run time. The first question when diagnosing a CI
failure is **"which commit is this run for?"**, not "what does the log say?".
Mechanism: `gh run view <run-id> --json headSha` (or the run header) — cross-
reference against the commit under diagnosis. Worked example: Step 13 Commit 2.
A diagnosis read a red CI log and assumed it was commit `d7e52ff`'s run,
drafting a "recovery" commit to add a baseline wrapper that was **already
correctly present**. In fact `d7e52ff` had never been pushed — it was local-only;
the red run was the prior commit `407c68f` (plan doc, _old_ `ci.yml`, no
wrapper). The log described the workflow at `407c68f`'s tree-state. Reading the
log without `headSha` verification produced a recovery for a non-existent
problem; pushing `d7e52ff` unchanged turned CI green on the first run.
